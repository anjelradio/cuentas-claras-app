# Research: Event Management Backend

## Technical Context Unknowns Resolved

### Better Auth `user` table mapping
- **Decision**: Create a proxy `User` model in SQLModel without inheriting from `BaseModel` (since `BaseModel` enforces a UUID `id` field and `user` table has `id` as `text` created by Better Auth).
- **Rationale**: The user ID is generated by Better Auth as a standard string. Our `events` and `event_members` tables need a foreign key to `user.id`. To satisfy SQLAlchemy relationships, we need a lightweight representation of the `user` table. 
- **Alternatives**: Use raw strings without explicit foreign keys in SQLAlchemy, but this sacrifices referential integrity in migrations.

### Emojis Mapping
- **Decision**: The `icon` field in `events` will be a standard `str` field (mapped to `VARCHAR` or `TEXT` in Postgres). 
- **Rationale**: The frontend defines a set of emojis (`['✈️', '🍕', '🍻', '🚗', '⛰️', '🏡']`). These are standard unicode characters and can be stored natively in Postgres without any special encoding beyond standard UTF-8.

### Status Enumerations
- **Decision**: Use Python `enum.Enum` mapped to strings for `EventStatus` (`open`, `closed`) and `MemberStatus` (`active`, `left`, `removed`).
- **Rationale**: Simplifies validation at the FastAPI schema level and ensures consistency in the database.

### Event Invitations Token Generation
- **Decision**: Use Python's `secrets` module to generate a 6-character alphanumeric string.
- **Rationale**: `secrets.choice(string.ascii_letters + string.digits)` provides cryptographically strong random tokens suitable for invite links.
